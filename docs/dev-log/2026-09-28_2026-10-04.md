1. **다리 목재가 서로 끊겨 보임**
   - **오류/발견**: 사용자 제공 화면 검토에서 설치 목재가 연속 다리보다 징검다리처럼 보였다.
   - **Root Cause**: `BridgeLog` 몸체는 49×1.4 ≈ 68.6 SVG 단위까지 그리지만 배치 간격은 75단위라 각 구간에 약 6.4단위 틈이 있었다.
   - **해결**: 설치된 길이만큼 이어지는 둥근 받침을 log segment 뒤에 렌더링했다. 담이는 설치된 구간 길이에서 위치를 계산한다.
   - **검증/상태**: 실제 화면의 0·25·50·75·100%에서 0·5·10·15·20개 설치와 연속 데크를 확인했다. 완료.

2. **작업별 헤더가 하나의 순서로 섞임**
   - **오류/발견**: 자기소개서/이력서/면접 경로에 지원 정보부터 최종 점검까지 총 6개 링크가 같은 nav에 표시됐다.
   - **Root Cause**: 모든 업무 경로가 단일 전역 `steps` 배열을 렌더링했다.
   - **해결**: 독립된 세 작업 선택 nav를 두고 자기소개서 경로에서만 지원 정보·경험·자기소개서·최종 점검 하위 nav를 표시한다. 현재 작업과 저장 상태를 헤더에 보여준다.
   - **검증/상태**: 세 작업 각각 1920×1080/1366×768 화면을 캡처했다. 인터뷰/이력서에서 자기소개서 하위 nav가 나오지 않고 overflow가 없음을 확인했다. 완료.

3. **입력 후 진행률이 바뀌지 않는 것처럼 보임**
   - **오류/발견**: 실제 코드·store를 추적했으며 고정 mock 값, 잘못된 memo dependency, store 구독 누락은 발견되지 않았다. 각 입력은 `WorkProvider.update()`를 거쳐 React 상태와 localStorage 저장 effect로 흐른다.
   - **Root Cause**: 진행률은 글자 입력량이 아니라 의미 있는 완료 조건으로 계산된다. 예를 들어 면접 답변은 내용 입력만으로 완료되지 않고 사용자가 ‘답변 완료’를 눌러 `done` 상태를 설정해야 한다. 자기소개서도 확인 체크와 요구 필드 완료 조건이 있다. 이전 App은 route가 바뀐 뒤 effect에서 `work.kind`를 동기화하므로 전환 첫 render가 직전 작업 종류일 수 있었다.
   - **해결**: `calculateWorkProgress()`와 공통 `bridgeMetrics()`를 추가하고 현재 route 종류를 계산에 동기적으로 전달했다. 완료 판단 규칙 자체는 유지해 입력하지 않은 사실이 진행률을 올리지 않게 했다. 다리 %·설치 목재·담이 위치를 동일 계산 결과에서 렌더링한다.
   - **검증/상태**: 실제 면접 화면에서 빈 답변 0%, 입력 후 미완료 0%, 답변 완료 후 20%/4개, 두 번째 완료 후 40%/8개를 확인했다. 새로고침 후 같은 답변·40%·8개·담이 위치가 복원됐다. 완료.

4. **시작 자재와 목적지 표현 누락**
   - **Root Cause**: 기존 `BridgeLandscape`에는 물·둔덕·나무·돌만 있고 자재 더미나 건물이 없었다.
   - **해결**: `BridgeMaterials`와 `DestinationBuilding`을 비버 담이/다리와 같은 색상 및 선 두께의 SVG로 추가했다. 완료 위치에서 bridge deck는 양쪽 둔덕에 닿는다.
   - **검증/상태**: 0%와 100% 및 양쪽 영역 개별 캡처에서 시작 재료·다리·작은 오두막을 확인했다. 완료.

5. **애니메이션 확인**
   - **Root Cause**: 공식 `dami-build.gif`는 이미 망치 동작 18프레임이지만 BridgeProgress에서 정지/carry 상태로 쓰였고, read 포즈는 정지 PNG만 있었다.
   - **해결**: BridgeProgress 진행 중에는 원래 build GIF를 선택해 담이가 현재 다리 끝에서 망치를 움직이게 한다. read 정지 그림에는 작은 SVG 페이지가 CSS로 넘겨지도록 적용한다. 사용자의 reduced-motion 설정에서는 움직임을 끈다.
   - **검증/상태**: 원본 build GIF의 0/4/9/14/17 프레임과 화면 내 page-turn 상태를 캡처했다. GIF 원본은 스타일을 보존하고 적합한 기존 움직임을 재사용하므로 변경하지 않았다. 완료.

6. **사용자 시각 검토: 자재·목적지·퍼센트 배치 보정**
   - **문제/발견**: 첫 후속 화면에서 자재의 각진 SVG 면이 판자 더미로 읽히고, 오른쪽 지붕형 실루엣은 회사 건물과 맞지 않았으며 장식 레이어가 퍼센트 배지를 가렸다.
   - **Root Cause**: 자재를 통나무 단면보다 상자형 다각형으로 그렸고 목적지 landmark를 사무실이 아닌 오두막으로 해석했다. 배지와 뒤쪽 풍경 레이어에 같은 stacking level이 적용돼 DOM 뒤쪽의 building SVG가 위에 그려졌다. 배지 오른쪽에도 장면 예약 폭이 없었다.
   - **해결**: 자재를 둥근 원목 몸통과 단면 나이테가 보이는 3단 적재로 바꾸고, 평지붕·창문 격자·‘회사’ 간판이 있는 그림책풍 사무실로 교체했다. 배지에 우측 예약 공간을 주고 장면보다 높은 stacking order로 올렸다.
   - **검증/상태**: 1920×1080에서 badge x=1638~1706, office container x=1764~1914이고, 1366×768에서 badge x=1166~1234, office x=1255~1362여서 두 화면 모두 겹치지 않는다. 실제 캡처에서 원목 단면·회사 간판·진행률을 확인했다. 완료.

#### 실패한 검증 시도

- 첫 전체 회귀에서 헤더에 저장 상태를 추가한 뒤 기존 테스트의 `getByText('임시저장 완료')`가 헤더와 SaveBar 두 요소를 찾는 strict-mode 오류가 발생했다. `저장 실패` 테스트에도 같은 중복이 있었다. 각 검증을 `.work-save-status`로 좁힌 뒤 전체 테스트를 재실행했다.
- 첫 캡처 명령은 Playwright 테스트 종료 뒤 5173 dev server도 함께 내려가 `page.goto: net::ERR_CONNECTION_REFUSED at http://127.0.0.1:5173/application`이 났다. 로컬 Vite dev server를 다시 켜고 독립 캡처를 재실행했다. 첫 시도 폴더는 비어 있으며 최신 이력은 새 번호 폴더로 저장했다.
