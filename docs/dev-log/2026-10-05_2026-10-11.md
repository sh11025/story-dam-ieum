## 2026-10-06 — 저장·PDF 입력 안정화 및 코드/산출물 조사

### 변경한 기능

- localStorage 임시 저장이 성공한 경우에만 이전 저장 오류를 지우도록 했다. 저장 실패 직후에는 오류를 유지하고 `저장 실패` 상태를 표시하며, 다음 저장 성공 뒤 `임시저장 완료`로 바뀐다.
- 문서 읽기 결과에 PDF의 전체 페이지 수, 처리 페이지 수, 잘림 여부를 담는다. 기존 최대 100페이지 상한은 유지한다.
- PDF가 100페이지를 넘으면 지원 정보·경험·이력서 파일 가져오기 화면에 전체 페이지 수, 읽은 범위, 제외된 페이지 범위를 알린다. 100페이지 이하 PDF에는 잘림 안내를 표시하지 않는다. 텍스트를 추출하지 못한 긴 PDF도 오류에 제외 범위를 함께 표시한다.
- `serviceStatus`는 전체 코드·문서·테스트 검색에서 선언 외 사용처를 찾지 못해 제거했다. `SupportAdapter`와 `AdminAdapter`는 README가 향후 서버 연결 경계로 명시하므로 유지한다.
- `work/`를 runtime, tests, scripts, docs, DEV_LOG 관점에서 분류했다. 실행 시 사용되는 테스트 입력/출력과 검증 스크립트, 과거 캡처·백업·중간 산출물이 함께 있어 이번 작업에서는 삭제하지 않았다. `artifacts/screenshots/`와 `src/assets/dami/`는 보존했다.

### 문제, Root Cause, 해결

1. **저장 실패 안내가 이후 성공 뒤에도 남음**
   - **현상/발견**: 읽기 전용 점검에서 확인한 동작을 현재 코드로 재확인했다. `localStorage.setItem()` 실패 경로는 `error`를 설정했지만 성공 경로는 `saveStatus`만 갱신했다.
   - **Root Cause**: 성공한 저장이 이전 `error` 상태를 clear하지 않는 코드 경로였다.
   - **수정 파일/방법**: `src/store.tsx`. `localStorage.setItem()`과 직렬화가 예외 없이 끝난 뒤에만 `setError('')`를 호출한다. 실패 시점에 오류를 먼저 지우지 않는다.
   - **검증**: Browser E2E에서 localStorage 쓰기를 강제로 실패시켜 오류를 확인하고, 실패 중에도 `.sdi` 파일 저장이 동작하는 것을 확인했다. 저장 함수를 복구하고 내용을 다시 변경한 뒤 성공 상태 및 오류 안내 제거를 확인했다.
   - **상태**: 완료.

2. **100페이지 초과 PDF 내용이 조용히 생략됨**
   - **현상/발견**: `src/services.ts`에서 `Math.min(doc.numPages, 100)`을 사용해 100페이지까지만 읽고 있었으며, 반환값은 텍스트뿐이었다.
   - **제한 이유 확인**: `README.md`의 알려진 범위에 텍스트 PDF 최대 100페이지가 명시되어 있다. 코드 주석·설계 문서에는 100이라는 수치의 구체적인 성능/메모리 근거가 없어 정확한 기술적 이유는 확인하지 못했다. 기존에 문서화된 지원 상한으로 판단해 제한은 유지했으며, 성능 보호라고 단정하지 않았다.
   - **수정 파일/방법**: `src/services.ts`, `src/pages.tsx`. 읽기 결과에 `totalPages`, `processedPages`, `truncated` metadata를 추가했다. 100페이지를 넘으면 예를 들어 전체가 101페이지일 때 1~100페이지만 가져왔고 101페이지는 읽지 않았다고 세 파일 가져오기 화면에 표시한다.
   - **검증**: PDF fixture 100페이지에서 마지막 페이지 텍스트까지 읽고 제외 안내가 없는 것을 확인했다. 101페이지 fixture에서는 1~100페이지만 읽고 원문 UI에 101페이지 텍스트가 없는 것, 안내에 전체 101페이지와 제외 범위가 표시되는 것을 Browser E2E로 확인했다. 101페이지 스캔형(텍스트 없는) fixture에서도 텍스트 추출 오류와 제외 범위 안내가 함께 표시되는 것을 확인했다.
   - **상태**: 완료. 제한의 기술적 근거는 미확인으로 남긴다.

3. **검증 선택자 오류 — 첫 PDF E2E 실행**
   - **현상**: 첫 테스트에서 `getByRole('status')`가 저장 상태, 다리 진행 상태, 파일 읽기 안내의 세 요소를 찾아 strict-mode 오류가 났다.
   - **Root Cause**: 테스트가 페이지 내 `status` 역할을 가진 여러 요소를 구분하지 않고 선택했다. PDF 처리 기능 오류는 아니었다.
   - **해결**: 파일 읽기/페이지 제외 문구를 기준으로 locator를 좁혔다.
   - **검증**: PDF 100·101페이지 targeted E2E와 최종 전체 Browser E2E를 다시 실행했다.
   - **상태**: 해결.

4. **검증 흐름 오류 — 스캔형 PDF E2E 추가 실행**
   - **현상**: 100페이지 및 101페이지 텍스트 PDF를 연속 확인한 뒤, 101페이지 스캔형 PDF를 올리는 단계에서 전체 테스트 실행을 중단했다.
   - **Root Cause**: 성공한 파일 가져오기는 붙여넣기 탭으로 돌아가지만 테스트는 파일 업로드 탭을 다시 선택하지 않았다. 업로더가 없는 상태에서 파일 입력을 기다리는 테스트 흐름 오류였다.
   - **해결**: 세 번째 PDF 업로드 전 파일 업로드 탭을 다시 선택하도록 테스트를 수정했다.
   - **검증**: 스캔형 PDF targeted test 통과 및 최종 전체 Browser E2E 13/13 통과.
   - **상태**: 해결.

## 2026-10-06 — 자기소개서·이력서·면접 독립 workflow

### 추가·변경한 기능

- 홈의 자기소개서, 이력서, 면접 준비 진입점은 독립적으로 유지했다. 이력서와 면접은 자기소개서 완료 없이 바로 시작할 수 있다.
- 작업 상단을 다른 작업으로 이동하는 메뉴와 현재 작업 표시로 구분했다. 자기소개서 내부 단계는 자기소개서 화면에서만 표시하고, 이력서·면접에는 다른 작업의 순차 단계를 표시하지 않는다.
- 작업별 진행률 계산을 별도 함수로 분리했다. 자기소개서는 지원 정보·선택 경험·문항·점검, 이력서는 필수 기본 정보와 작성 대상으로 켠 section, 면접은 사용자가 완료 표시한 답변을 기준으로 계산한다. 페이지 위치나 다른 작업 진행률을 사용하지 않는다.
- 지원 정보·경험은 기존 Work 데이터의 단일 원본을 계속 사용한다. 이력서와 면접은 이를 참고 정보로 보여주며 자기소개서 답변·이력서 항목으로 자동 복제하거나 덮어쓰지 않는다. 면접은 이력서의 작성 항목도 참고할 수 있다.
- 이력서 또는 면접에서 편집할 때 자기소개서 점검 체크가 초기화되지 않도록 했다. 자기소개서 작업에서 편집할 때만 기존 점검 무효화 규칙을 적용한다.
- 작업별 퍼센트 하나로 bridge 목재 수와 담이 위치를 계산한다. 왼쪽 원목, 연결된 deck, 오른쪽 회사 건물의 기존 일러스트를 유지했다.
- Playwright E2E에 작업 전환, 공유 지원 정보·경험·이력서 참고 정보, 독립 진행률, 새로고침, 면접 `.sdi` 복귀 시나리오를 추가했다.

### 데이터 구조 및 호환성

- `Work` 안의 기존 `application`, `experiences`, `letters`, `resume`, `interview`, `review` 구성을 유지했다. 지원 정보와 경험은 공유 데이터이고 나머지는 해당 작성 작업 데이터다.
- `.sdi` `formatVersion: 1` 및 스키마를 변경하지 않았다. 따라서 이 작업에서 구형 `.sdi` migration은 필요하지 않으며, 브라우저와 E2E에서 기존 형식 저장·불러오기를 확인했다.
- Resume DOCX/PDF 내보내기와 Cover Letter DOCX/PDF 내보내기 로직은 재작성하지 않았다. 기존 브라우저 테스트에서 두 문서 형식 내보내기가 계속 동작하는 것을 확인했다. 면접 내보내기는 추가하지 않았다.
- admin, support, login/backend 경로는 변경하지 않았고 독립 작업 진행률에도 연결하지 않았다.

### 오류, Root Cause, 해결

1. **작업 전환 E2E의 불명확한 버튼 선택자**
   - **현상**: 첫 실행에서 `작업 불러오기` 부분 이름이 홈 카드와 가져오기 확인 대화상자 버튼 두 곳에 일치해 strict-mode 오류가 발생했다.
   - **Root Cause**: 테스트가 이름 전체 일치를 제한하지 않았다. 앱 저장/불러오기 동작 오류는 아니었다.
   - **해결**: 대화상자 확인 버튼에 `exact: true`를 적용했다.
   - **검증**: 해당 독립 workflow E2E 재실행 통과, 이후 전체 Playwright 14/14 통과.
   - **상태**: 해결.

2. **테스트/빌드 프로세스 권한 제한**
   - **현상**: 기본 sandbox 실행에서 Playwright worker와 esbuild service의 child process가 `spawn EPERM`으로 시작하지 못했다.
   - **Root Cause**: 해당 실행 환경의 프로세스 생성 제한이었다. 소스 컴파일 오류로 판단하지 않았다.
   - **해결**: 사용자 프로젝트 범위의 Playwright 및 build 검증 명령을 권한 확장으로 재실행했다.
   - **검증**: TypeScript, lint, 전체 Browser E2E 14/14, production build 통과.
   - **상태**: 해결.

## 2026-10-06 — Dami animation 및 BridgeProgress 최종 연출

### 추가·변경한 기능

### 오류, Root Cause, 해결

1. **refresh 회귀 테스트가 중간 애니메이션 상태를 저장 상태로 오인**
   - **현상**: 전체 테스트 첫 실행에서 60% progress와 설치 목재 수가 잠깐 다르다고 실패했다.
   - **Root Cause**: UI의 실제 업무 진행률은 즉시 60%가 되었지만, 테스트가 940ms 건설/설치 연출이 끝나기 전에 refresh를 실행하고 과거 설치 수와 복원된 최종 설치 수를 비교했다. 제품의 refresh 동작은 저장된 진행률에서 최종 다리 상태를 복원한다.
   - **해결**: refresh 전 bridge visual progress가 업무 진행률에 수렴했는지 기다리도록 회귀 테스트를 수정했다.
   - **검증**: 최종 전체 Browser E2E 16/16 통과.
   - **상태**: 해결.

2. **100% 연출 테스트의 중간 상태 전제와 신규 통나무 수 불일치**
   - **현상**: 초기 테스트는 다섯 답변을 즉시 완료한 다음 0% 상태가 계속 유지된다고 가정했고, 100% 구간에서 새로 설치된 목재 20개를 기대했다.
   - **Root Cause**: 테스트 입력 도중 실제 진행/애니메이션이 계속 갱신될 수 있는데 초기값을 고정 전제했으며, 80%에서 100%로 갈 때 새로 설치되는 수는 전체 20개가 아니라 마지막 4개다.
   - **해결**: 4개 답변(80%)의 설치 완료를 확인한 뒤 마지막 답변을 완료하고, 80→100 전환의 phase 및 추가 4개 강조를 검증하도록 시나리오를 고쳤다.
   - **검증**: targeted 100% 전환 Browser E2E 통과, 뒤이어 최종 전체 16/16 통과.
   - **상태**: 해결.

3. **권한 제한으로 build worker가 시작하지 못함**
   - **현상**: 기본 실행의 Vite/esbuild 단계가 `spawn EPERM`으로 종료됐다.
   - **Root Cause**: 실행 sandbox의 child-process 제한. TypeScript 검사와 린트는 같은 환경에서 통과했다.
   - **해결/검증**: 승인된 프로젝트 범위 명령 권한으로 production build를 재실행해 성공했다.
   - **상태**: 해결. 기존 500kB 초과 chunk 경고는 남아 있으며 이번 작업에서 chunk 구성을 변경하지 않았다.
